## 1. 项目概述

### 1.1 编写目的

本项目拟为湖北工程学院新技术学院建设一套面向多类访问者的 Web 端校园导览系统。公众进入页面后，可以直接在三维校园场景中漫游，通过文字或普通话语音与数字人导览员交流，获得建筑介绍、步行导航、校园信息问答和场景控制服务。系统同时提供独立管理后台，用于维护点位资料、知识库、FAQ、精品路线、对话日志、统计结果和运行参数。

本 PRD 的目标是明确“系统为谁解决什么问题、必须提供哪些能力、达到什么质量水平、如何验收”，并为以下后续成果提供稳定输入：

1. 概要设计中的总体架构、模块边界、部署拓扑和数据库概要。
2. 详细设计中的实体、接口出入参、意图识别、RAG、路径规划和数字人状态机方案。
3. 编码阶段的模块拆分、测试边界和联调契约。
4. 测试阶段的用例来源和验收依据。
5. 部署运维阶段的配置项、容量目标和故障降级要求。

### 1.2 项目背景

高校校园导览通常依赖静态地图、图文介绍或人工咨询。考生家长关注学校概况和专业信息，新生关注报到、宿舍和办事地点，在校师生需要快速定位建筑和校园服务，校外访客需要了解参观路线。现有信息往往分散在新闻、招生网页、图片和临时通知中，三维空间关系与文字信息没有形成统一入口。

本项目通过轻量化三维场景、可配置点位、私有知识库和数字人交互，将这些需求集中到一个 Web 平台。系统的重点不是制作高精度建筑动画，而是在可控资源下解决“看懂校园、找到地点、问到可信信息、获得连续导览体验”四类问题。

### 1.3 产品定位

产品定位为面向本科毕业设计的可演示、可维护、可扩展校园数字导览原型，并具备向学校正式门户子站点演进的技术边界。系统支持桌面浏览器和移动浏览器访问，公众端不需要注册登录；后台端采用管理员鉴权。

“数字孪生”在本项目中指基于轻量化建筑、道路、广场和点位坐标构建的可交互三维表达，不承诺 BIM 级构件精度、室内精细建模或实时物理仿真。

### 1.4 建设目标

| 目标编号 | 目标 | 可观察结果 |
| --- | --- | --- |
| G-01 | 建立可交互的三维校园入口 | 用户首屏看到校园场景，可旋转、缩放和平移，能识别并点击核心点位 |
| G-02 | 建立自然的多模态导览入口 | 用户可通过文字或普通话语音提问，系统能区分四类核心意图并执行对应动作 |
| G-03 | 建立校园事实的可信回答机制 | 校园事实只来自已审核知识库、FAQ 或结构化点位资料；无依据时统一拒答并引导官网 |
| G-04 | 建立空间与语言的联动引导 | 讲解时镜头飞到点位并高亮，导航时展示贴合道路网的发光路线并进行语音指引 |
| G-05 | 建立可运营的内容后台 | 管理员可维护点位、路线、机位、文档、FAQ、参数和日志，普通公众不能进入 |
| G-06 | 建立可验证的工程质量 | 关键算法独立可测，性能、并发、安全、降级和验收指标明确 |

### 1.5 成功标准

第一阶段需求通过后，项目应满足以下产品级成功标准：

1. 至少 10 个核心校园点位、3 条精品路线和 6 个预置机位可在后台配置并发布。
2. 四类核心意图在不少于 300 条标注测试集上的宏平均 F1 不低于 0.90。
3. 对已录入并审核的校园问题，检索回答应给出可追溯来源；对知识库无依据的问题，不得输出学校具体事实。
4. 桌面端和移动端均可完成“进入场景、询问问题、查看讲解、获取路线”的主任务。
5. 在指定的基准设备和 4G 网络条件下，达到本文规定的首屏、帧率和响应时延目标。
6. 后台内容修改、发布、过期和重新向量化均有状态记录，可审计、可回滚到上一发布版本。

## 2. 范围与边界

### 2.1 本期范围

| 范围域 | 本期必须覆盖的内容 |
| --- | --- |
| 公众三维场景 | 轻量校园总体场景、核心建筑与道路广场、鼠标和触控漫游、点位交互、预置机位 |
| 数字人 | 悬浮展示、待机动画、表情、手势、播报状态、唇形同步、字幕和语音开关 |
| 多模态交互 | 文字输入、按住说话、普通话识别、四类意图识别、歧义澄清、多轮指代 |
| 空间导览 | 建筑讲解、镜头飞行、目标高亮、道路网步行导航、方向箭头、分步语音 |
| 知识问答 | 私有 RAG 文档管理、解析分片、向量化、检索、来源引用、无依据统一拒答、FAQ 优先 |
| 精品路线 | 新生报到、校园参观、生活服务等可配置路线，按点位顺序自动飞巡和讲解 |
| 管理后台 | 管理员登录与权限、点位、路线、机位、文档、FAQ、日志、统计和参数管理 |
| 离线演示 | 本地兜底数据、固定 FAQ、场景漫游和降级提示，确保无外网时仍能演示主流程 |
| 工程质量 | 统一响应格式、全局异常处理、日志追踪、权限、安全、备份和可测试性要求 |

### 2.2 本期不包含

1. 室内逐层导航、电梯路线、无障碍实时避障和真实定位。
2. 校园门禁、支付、选课、成绩、迎新系统写入等业务系统集成。
3. 面向个人的注册账户、收藏、历史同步和社交功能。
4. 高精度 BIM、实景三维扫描、照片级写实建筑、室内家具和车辆物理仿真。
5. 校园事实的自动抓取入库和未经人工审核的自动发布。
6. 录取结论、政策解释、紧急救援等需要学校正式授权的专业服务。

### 2.3 范围控制原则

新增需求应说明其所属模块、对性能与工期的影响，以及是否可在不改变本期验收范围的情况下实现。任何涉及学校正式名称、位置、开放时间、报到流程和专业政策的内容，均须经过来源核验和校内审核，不能以开发人员推测替代。

### 4.3 事实来源优先级

同一信息出现多个版本时，系统采用以下优先级，并在管理后台显示其来源和生效时间：

1. 学校最新正式发布并经本项目审核的年度文件。
2. 学校官网当前公开页面。
3. 学校相关部门书面确认的项目资料。
4. 已审核的历史资料，仅在其有效期和适用范围明确时使用。
5. 没有上述依据时，不生成具体学校事实。

“招生章程”“新生入学指南”等季节性资料必须记录适用年度和失效日期。超过有效期后，系统不得把旧年份的日期、流程或政策直接当作当前信息回答。

### 4.4 统一无依据回复

当知识库、FAQ 和结构化点位资料均无可用依据，或检索结果置信度低于配置阈值时，系统必须返回统一模板，不调用大模型自由补充学校事实。建议固定文案为：

> 暂时无法回答这个问题。该问题未在已审核的校园知识库中找到可核验信息，请访问湖北工程学院新技术学院官网（https://www.hbeutc.cn/）或联系学校相关部门确认。

离线且无法访问官网时，可追加“当前网络不可用，请联网后访问官网或使用页面提供的学校联系方式”。文案不得暗示学校确认了知识库中不存在的内容。

### 5.2 三维校园场景

#### 5.2.1 场景内容

| 编号 | 优先级 | 需求描述 |

| FR-SCENE-001 | 必须 | 使用 Three.js 构建可交互校园总体场景，至少包含轻量建筑体块、屋顶、入口标识、道路、广场、绿地和必要环境光照 |
| FR-SCENE-002 | 必须 | 首期可发布点位不少于 10 个，覆盖校门、教学或实验建筑、图书馆、学生公寓、食堂、运动场、行政或服务中心等核心功能类别；无法确认的正式名称和坐标必须保持待审核状态 |
| FR-SCENE-003 | 必须 | 建筑、道路和点位通过后台配置与三维资源标识关联，更换或调整点位时无需修改前端核心代码 |
| FR-SCENE-004 | 必须 | 用户可通过鼠标拖拽旋转、滚轮缩放、右键或组合手势平移；移动端支持单指旋转和双指缩放 |
| FR-SCENE-005 | 必须 | 相机移动和缩放应有边界，不能穿入地面、永久丢失目标或因极端缩放导致失控 |

| FR-SCENE-008 | 宜 | 建筑名称在合适缩放级别显示，远景显示图标或聚合标记，避免标签重叠 |
| FR-SCENE-009 | 宜 | 支持简单昼夜光照或中性色调切换，但不得改变学校事实性标识 |
| FR-SCENE-010 | 必须 | 当设备无法稳定运行 WebGL 时，提供二维平面图或静态导览降级模式，并说明三维功能不可用 |

#### 5.2.2 场景数据与呈现约束

1. 建筑采用单体白模或低多边形建模，重点通过体量、入口、材质色块和名称标识辨识；不要求室内构件、室内家具或照片级纹理。
2. 道路和广场必须与导航路网保持空间一致，视觉道路与实际可行路线不得互相矛盾。
3. 初始网络载荷应控制在第 8 章规定范围内。远景建筑和次要纹理按需加载，首屏只加载主视角可见资源。
4. 点位、路线、机位和游览顺序均由后台数据驱动。三维模型尺寸和坐标采用统一单位，并通过导览调试模式可视化检查。
5. 学校校名、校徽、建筑正式名称和校园照片只能在来源明确且获得发布授权后使用。

### 5.5 意图识别与对话管理

#### 5.5.1 核心意图

| 意图编号 | 意图名称 | 示例 | 系统动作 |
| --- | --- | --- | --- |
| INTENT-01 | 建筑介绍 | “介绍一下图书馆”“科技楼是做什么的” | 绑定目标点位，镜头飞行，高亮，数字人讲解 |
| INTENT-02 | 步行导航 | “从校门怎么去食堂”“带我去图书馆” | 解析起点和终点，计算道路网路径，绘制导向线并分步播报 |

| 状态 | 用途 |
| --- | --- |
| CLARIFY | 目标、起点、终点或场景动作不明确，需要用户补充或选择 |
| UNKNOWN | 与校园导览无关、无法分类或超出系统服务范围 |

#### 5.5.2 识别与响应规则

| 编号 | 优先级 | 需求描述 |
| --- | --- | --- |
| FR-INTENT-001 | 必须 | 对每条文本或语音转写，输出唯一主意图、置信度、目标点位、起点、终点和场景动作等结构化结果 |

| FR-INTENT-003 | 必须 | 当最高置信度低于配置阈值或前两类差距过小时，进入 CLARIFY，不得贸然执行镜头飞行、路线规划或事实回答 |
| FR-INTENT-004 | 必须 | 同一句话包含多个动作时，系统按可解释顺序处理；若动作存在冲突，应向用户确认主任务 |
| FR-INTENT-005 | 必须 | 支持点位别名、错别字、常见口语简称和语音识别近音词；别名由后台维护 |
| FR-INTENT-006 | 必须 | 对未识别的校外、无关或超范围问题，明确说明只能提供校园导览和已审核校园信息 |
| FR-INTENT-007 | 必须 | 模型或规则不可用时降级到关键词和别名匹配，并对低置信结果要求点击选择，不伪造识别成功 |

#### 5.8.2 问答流程

| 编号 | 优先级 | 需求描述 |
| --- | --- | --- |
| FR-RAG-009 | 必须 | 问答按“问题规范化 → FAQ 精确或高相似匹配 → 私有知识库检索 → 证据阈值判断 → 大模型组织回答”的顺序处理 |

| FR-RAG-014 | 必须 | 对时间敏感问题，系统应优先选择适用当前日期的已发布资料；无法判断时效时明确说明并拒绝给出生效结论 |
| FR-RAG-015 | 必须 | 回答不得泄露后台文档原文中的系统提示、密钥、管理员信息或未发布内容 |
| FR-RAG-016 | 必须 | 检索召回率 Recall@5 在不少于 100 条已标注问题集上不低于 0.85；校园事实回答的可追溯来源覆盖率为 100% |

## 7. 业务规则

| 规则编号 | 业务规则 |
| --- | --- |
| BR-01 | 系统核心业务意图固定为建筑介绍、步行导航、校园信息问答和场景控制四类；CLARIFY 与 UNKNOWN 是控制状态，不应被统计为第五类或第六类业务意图。 |
| BR-02 | 学校具体事实必须来自当前有效的已审核资料。大模型只负责组织语言，不负责创造学校事实。 |
| BR-03 | 无检索依据、证据时效不明或证据与问题不相关时，使用统一拒答模板并引导访问学校官网。 |
| BR-04 | FAQ 的可信优先级高于一般知识库检索；但过期、未审核或与当前官方文件冲突的 FAQ 不得命中。 |
| BR-05 | 时间敏感资料必须记录适用年度、发布日期、失效日期和审核人。新生报到、开放时间和招生政策是重点检查对象。 |
| BR-06 | 路线只能沿已配置的可通行道路节点和边生成，不得以直线替代真实道路，也不得绕过模型障碍生成无法行走的捷径。 |
| BR-07 | 用户说“那里”时，只允许绑定当前会话中最近且仍有效的明确实体；存在歧义时先澄清。 |
| BR-08 | 镜头飞行、数字人播报、路线动画和语音控制应互斥协调；新的用户动作可中断旧动作，但界面状态必须同步更新。 |
| BR-09 | 点位、路线、机位、文档和 FAQ 必须遵循草稿、待审核、已发布、已过期、已下线、已归档等生命周期，公众只能读取已发布且当前有效的内容。 |
| BR-10 | 删除被引用的点位或知识文档时，应阻止硬删除并要求归档或解除引用，保证历史日志可追溯。 |
| BR-11 | 学校正式名称、校徽、建筑名称、图片和模型必须确认授权来源；演示占位内容必须在后台明确标记，不得用相似名称冒充官方信息。 |
| BR-12 | 麦克风录音必须由用户主动触发，页面需说明用途。原始录音默认不作为业务数据长期保存。 |
| BR-13 | 每次回答、路线、镜头和数字人动作应可通过会话标识和追踪标识关联，便于问题定位。 |
| BR-14 | 第三方能力失败时优先保证“文字可读、场景可用、路线可演示、事实不编造”，允许语音体验降级但不得隐藏降级状态。 |
| BR-15 | 所有面向用户的时间、距离和开放状态均应标注其来源或为“预计值”。模拟步行时间不得声称为实时导航结果。 |
| BR-16 | 管理员操作必须遵循最小权限。审核、发布、删除、导出、重建索引等操作不能由公众或未授权会话执行。 |

## 8. 非功能需求

### 8.1 性能目标

性能测试应使用可重复的基准设备、网络条件和资源版本。发布前记录测试机配置、浏览器版本、校园模型资源版本、并发用户数和第三方服务状态。

| 编号 | 指标 | 目标值 | 测量条件与说明 |
| --- | --- | --- | --- |
| NFR-PERF-001 | 首屏可用时间 | 中位数不高于 3.0 秒，P95 不高于 5.0 秒 | 桌面参考设备，冷缓存，4G/10 Mbps 下行、80 ms RTT；这里定义为可看到场景外壳和主要入口，不是全部纹理加载完毕 |
| NFR-PERF-002 | 三维场景可交互时间 | 中位数不高于 6.0 秒，P95 不高于 8.0 秒 | 同上；主场景模型和首屏可见建筑加载完成 |
| NFR-PERF-003 | 首屏网络传输预算 | gzip 后 JavaScript 和样式不超过 1.5 MB；首屏场景几何、纹理和必要数字人资源不超过 12 MB；完整首屏总请求不超过 25 MB | 不含后续按需加载的次要资源；模型和贴图应压缩并使用合理的纹理尺寸 |
| NFR-PERF-004 | 桌面帧率 | 基准场景下平均不低于 50 FPS，P95 帧间隔不高于 33 ms | 1920×1080，中端独立显卡或同级集成显卡，基准浏览器 |
| NFR-PERF-005 | 移动帧率 | 中等画质平均不低于 30 FPS | 近三年主流中端手机，360 至 430 CSS px 宽度，移动浏览器；低画质模式可降低阴影和粒子 |
| NFR-PERF-006 | 场景交互反馈 | 点击、拖拽和缩放输入响应中位延迟不高于 100 ms | 不统计网络请求；不得因数字人播报或路径动画阻塞主线程 |
| NFR-PERF-007 | 语音识别等待 | 用户结束说话至看到转写中位不高于 2.5 秒，P95 不高于 5.0 秒 | 普通话、10 秒以内语音、正常网络和第三方服务正常 |
| NFR-PERF-008 | 文字问答完整响应 | 有可检索证据时 P95 不高于 5.0 秒，P99 不高于 8.0 秒 | 从提交到显示答案首屏或首段，不含用户阅读时间；语音播放可流式开始 |
| NFR-PERF-009 | 数字人首段语音起播 | TTS 请求到首段音频开始播放 P95 不高于 2.5 秒 | 已命中回答且第三方 TTS 可用；期间显示播报准备状态 |
| NFR-PERF-010 | 路径计算 | 500 个道路节点以内的路径计算 P95 不高于 800 ms | 单次请求、同一进程正常负载；不包含第三方服务 |
| NFR-PERF-011 | 路线首帧显示 | 路径计算完成后 300 ms 内出现完整路线和终点标记 | 不含首次资源下载时间 |
| NFR-PERF-012 | 镜头飞行 | 常规建筑切换 1.2 至 2.8 秒；用户设置可调，但不得无上限自动飞行 | 距离较远时可分段；用户输入可中断 |
| NFR-PERF-013 | 后台列表接口 | 1000 条规模内常规分页查询 P95 不高于 1.0 秒 | 不含上传、解析和向量化等异步任务 |
| NFR-PERF-014 | 页面内存 | 基准场景连续漫游 10 分钟后无非预期增长，浏览器内存增长不超过初始稳定值的 20% | 排除第三方浏览器缓存波动；检查几何体、材质、纹理和事件监听释放 |

### 8.2 并发与容量

| 编号 | 指标 | 目标值 |
| --- | --- | --- |
| NFR-CAP-001 | 公众端并发在线 | 支持 200 个同时在线会话；200 个会话下场景静态资源和普通查询不出现系统性故障 |
| NFR-CAP-002 | 同时活跃问答 | 支持 50 个同时进行的文本问答会话 |
| NFR-CAP-003 | 持续请求能力 | 文字导览请求达到 5 次/秒并持续 10 分钟，错误率不超过 1%，P95 响应符合 NFR-PERF-008 |
| NFR-CAP-004 | 语音请求能力 | 语音识别和语音合成各支持 2 个并发请求；第三方限流时应排队或降级，不拖垮其他请求 |
| NFR-CAP-005 | 路径计算能力 | 支持每秒 10 次路径计算，在 500 个节点规模下满足 NFR-PERF-010 |
| NFR-CAP-006 | 后台并发 | 支持 10 个管理员会话同时维护内容；重建索引时不影响公众端使用上一已发布索引 |
| NFR-CAP-007 | 扩展方式 | 容量不足时可通过增加后端实例、拆分 AI 调用服务或独立向量检索服务扩展；前端不应依赖单一进程的本地内存状态 |

以上容量目标是本科项目验收基线，不等同于学校生产环境承诺。正式上线前应按实际日活、第三方配额和预算重新压测。

### 8.3 可用性与可靠性

| 编号 | 指标 | 目标值 |
| --- | --- | --- |
| NFR-REL-001 | 公众服务可用性 | 计划上线月份内不低于 99.5%，不含预先公告维护窗口 |
| NFR-REL-002 | 后台服务可用性 | 不低于 99.0% |
| NFR-REL-003 | 故障恢复时间 RTO | 核心数据库或应用故障后 120 分钟内恢复基本服务 |
| NFR-REL-004 | 数据恢复点 RPO | 业务数据丢失不超过 24 小时；关键配置和已审核知识数据每日备份 |
| NFR-REL-005 | 第三方故障隔离 | 大模型、ASR、TTS 或向量服务任一不可用时，其他模块仍能提供定义好的降级能力 |
| NFR-REL-006 | 索引完整性 | 每次发布只切换完整索引版本；索引构建失败不替换当前可用版本 |
| NFR-REL-007 | 错误恢复 | 用户可重试失败的加载、识别、问答或上传任务，不因单次失败丢失已发布内容 |
| NFR-REL-008 | 幂等性 | 上传确认、向量化触发、参数保存和发布操作在重复提交时不能产生重复有效版本 |

### 8.4 安全与隐私

| 编号 | 安全需求 |
| --- | --- |
| NFR-SEC-001 | 公众端与后台端使用 HTTPS；生产环境不得通过明文 HTTP 传输账号、语音或知识文档。 |
| NFR-SEC-002 | 后台必须进行身份认证、角色授权和会话失效控制；所有后台写操作在服务端再次校验权限。 |
| NFR-SEC-003 | 密码采用安全的单向哈希和盐值策略；密钥、数据库密码和第三方令牌只存放在服务端环境变量或密钥配置中，不进入前端包和代码仓库。 |
| NFR-SEC-004 | 文件上传必须校验扩展名、MIME、文件签名和大小；限制可执行文件与危险内容；文件名不得直接作为服务器路径。 |
| NFR-SEC-005 | 所有外部输入均须进行长度、类型和内容校验；数据库访问参数化；页面输出防止脚本注入。 |
| NFR-SEC-006 | 公众问答和语音接口应有频率限制，后台登录应有失败次数控制和审计。 |
| NFR-SEC-007 | 知识库文档和检索片段应视为后台内容，未发布版本不得通过公众接口、错误信息或模型回答泄露。 |
| NFR-SEC-008 | 提示词注入防护属于业务安全要求：文档中的指令性文本不得改变系统事实来源、权限或拒答策略。 |

### 9.3 数据生命周期与质量管理

1. 点位、路线、机位、文档和 FAQ 应具有草稿、待审核、已发布、已过期、已下线和已归档状态；状态转换需记录操作者和时间。
2. 发布前必须校验名称、坐标或来源、有效期、内容归属和设备可见性。任何关键字段缺失时不得发布。
3. 时间敏感资料必须提供适用年度、发布日期、失效日期或至少一个有效期规则。到期后自动停止公开命中并进入待更新列表。
4. 文档重新上传和重新索引保留版本号；公众只使用已审核且有效的索引。回滚以版本为单位，不以单条随机片段为单位。
5. 点位别名可以有多个，但同一别名不能无提示地绑定多个公开点位。冲突时要求管理员选择主要点位。
6. 删除点位、文档、FAQ 和路线前检查引用关系。被历史日志、路线或知识片段引用时采用归档或下线。
7. 统计数据优先聚合，只保留必要匿名标识。原始录音默认不入库；如需调试留存，必须配置自动过期和访问控制。
8. 数据备份至少包含业务数据库、已发布文档元数据、索引构建配置和三维配置文件；模型大文件可采用可验证的版本化存储策略。

### 9.4 学校信息时效规则

| 数据类型 | 默认有效策略 | 过期处理 |
| --- | --- | --- |
| 学校基本身份、地址、办学层次 | 来源长期有效时持续有效，但每次重新审核 | 来源冲突或页面失效时进入待复核 |
| 招生专业、计划、政策和联系方式 | 以当年官方文件为准 | 下一招生年度未更新时只展示来源年份和官网入口，不给出当前承诺 |
| 开放时间、报到流程和路线 | 必须绑定日期范围或年度 | 超过结束日期后停止公开命中，转为待更新 |
| 点位介绍 | 由校方审核后长期有效 | 建筑名称或用途变化时由审核人员更新 |
| 临时活动信息 | 必须设置明确的开始和结束时间 | 到期自动隐藏，不参与 RAG 回答 |

## 10. 接口需求

### 10.1 接口分层

本阶段定义接口组和契约约束，不逐项给出 URL、字段名和数据库映射。完整接口清单及出入参在概要设计和详细设计阶段冻结。

| 接口组 | 使用方 | 主要职责 | 关键约束 |
| --- | --- | --- | --- |
| 公众场景初始化接口 | 公众前端 | 返回默认机位、已发布点位、路线和配置版本 | 不返回未发布内容、账号信息或内部调试字段 |
| 点位与搜索接口 | 公众前端 | 点位列表、别名搜索、点位详情和机位 | 只查询有效点位；分页和缓存可用 |
| 对话接口 | 公众前端 | 文字问题、意图、实体、动作、回答和来源 | 统一响应结构；可返回多步处理状态；超时有统一错误 |
| 语音识别接口 | 公众前端 | 上传短音频，返回普通话转写与状态 | 限制大小、时长和频率；不把原始音频写入长期存储 |
| 语音合成接口 | 公众前端 | 将已审核回答转换为音频和可选口型时间轴 | 支持流式或分段；失败时可退化为字幕 |
| 路线接口 | 公众前端 | 起终点解析、路径、距离、分段指引和导航状态 | 只使用已发布道路网络；无路径时给出明确业务错误 |
| 反馈与日志接口 | 公众前端 | 有帮助、无帮助、信息过期和匿名交互事件 | 不含敏感音频；可关联匿名会话和追踪标识 |
| 后台认证接口 | 管理前端 | 登录、退出、会话刷新和当前权限 | HTTPS；令牌不暴露在 URL；会话可失效 |
| 后台内容接口 | 管理前端 | 点位、路线、机位、FAQ、参数和账号维护 | 角色授权；写操作审计；冲突时返回明确错误 |
| 知识库接口 | 管理前端 | 文档上传、状态查询、重新向量化和索引发布 | 异步任务；文件校验；版本回滚 |
| 统计与导出接口 | 管理前端 | 日志筛选、聚合指标和导出任务 | 脱敏；数据角色最小权限；导出审计 |
| 外部 AI 适配接口 | 后端 | 统一接入大模型、ASR、TTS 和向量能力 | 使用标准兼容协议；超时、重试、限流和降级可控 |

### 10.2 统一响应与错误约定

1. 所有后端接口使用统一响应外壳，至少能表达业务结果、可读消息、数据负载、时间戳和追踪标识。不得让部分接口直接返回原始数组或第三方原始错误。
2. 业务错误与系统错误分开表达。参数错误、未认证、无权限、资源不存在、业务冲突、限流、外部服务不可用和未知异常应使用稳定错误类别。
3. 用户可见消息使用中文，技术细节写入服务端日志。前端只负责展示稳定错误消息和可操作建议。
4. 写接口在重复提交时必须具备幂等处理，尤其是发布、上传确认、重新索引和参数保存。
5. 列表接口支持分页和筛选；统计接口的日期范围必须有上限，避免一次导出拖垮数据库。
6. 公开接口和后台接口分域管理。公众端不得调用后台管理能力，后台管理接口不得通过仅隐藏前端菜单实现权限。
7. 外部服务调用必须具有明确超时、有限重试和失败分类。重试只用于可安全重复的请求，不得重复创建业务记录或重复播放冲突动作。
8. 对话和关键动作应携带追踪标识。前端展示的错误可由该标识在后台定位到对应日志。

### 10.3 AI 能力适配要求

| 能力 | 输入 | 输出 | 失败处理 |
| --- | --- | --- | --- |
| 大模型 | 已规范化的用户问题、检索片段、角色约束和输出要求 | 基于片段的回答、引用或“无法回答”结论 | 切换到 FAQ 原文或无依据拒答；不得改用模型记忆编造 |
| 语音识别 | 普通话短音频、语言设置和会话标识 | 转写文本、置信度、错误状态 | 返回文字输入提示或本地识别降级 |
| 语音合成 | 已审核的播报文本、语速、音量和可选口型时间轴 | 音频流或音频文件、时长、口型时间轴 | 播放字幕和轻量动作，显示语音不可用 |
| 向量化 | 标准化文本片段和模型标识 | 向量或任务状态 | 保留上一索引，继续使用可用检索版本 |
| 向量检索 | 查询向量、分类或过滤条件、返回数量上限 | 片段、相似度、来源和版本信息 | 本地关键词检索；低于阈值时统一拒答 |

第三方接口应通过后端适配器接入，前端不直接持有供应商密钥。适配器应保留统一的错误和降级语义，使更换供应商不改变公众端主要流程。完全本地部署的模型、轻量 FAQ 和规则检索可作为离线演示能力，但其回答范围必须清晰可见。

### 10.4 上传和异步任务约束

| 项目 | 要求 |
| --- | --- |
| 允许文档类型 | PDF、DOC、DOCX、TXT |
| 单文件大小 | 默认上限 50 MB，可后台配置；超过上限在客户端和服务端双重拒绝 |
| 批量上传 | 默认每次最多 5 个文件；超出时提示分批处理 |
| 文本提取 | 记录成功页数、失败页数和不可提取原因；扫描件提示需要 OCR |
| 异步任务 | 上传确认、解析、向量化、索引发布、统计导出均可异步执行，并展示进度或状态 |
| 任务重试 | 可重试失败任务，不覆盖成功版本；重试原因和次数可审计 |
| 取消操作 | 未开始或处理中任务可取消，取消后不发布部分索引 |

### 10.5 前端与场景的动作契约

用户意图与场景之间至少需要以下逻辑动作，详细字段在设计阶段定义：

| 逻辑动作 | 触发来源 | 必要结果 |
| --- | --- | --- |
| 聚焦点位 | 建筑介绍、点位点击、精品路线 | 相机移动到可观察位置，选中目标 |
| 高亮目标 | 建筑介绍、导航终点、路线站点 | 目标有可见但不破坏材质的闪烁状态 |
| 显示路线 | 导航意图 | 道路线、方向箭头、起终点和分段数据同时出现 |
| 清除路线 | 场景控制、导航结束 | 路线、箭头、播报和导航状态一致消失 |
| 切换机位 | 场景控制、后台预览 | 相机到达目标机位或提供明确失败原因 |
| 重置视角 | 场景控制 | 返回已发布默认机位 |
| 数字人播报 | 回答、讲解、分步导航 | 文字、音频、动作和口型状态同步 |
| 停止播报 | 用户控制 | 立即停止音频和后续口型，保留已有字幕 |
| 开始或暂停游览 | 精品路线控制 | 路线进度、相机和数字人状态一致 |

## 11. 验收标准

### 11.1 功能验收矩阵

验收分为“可演示、可重复、可验证”三类。功能已展示但没有稳定测试证据的，不视为通过。

| 验收编号 | 验收场景 | 通过条件 | 关联需求 |

| AC-01 | 首次访问公众端 | 无需登录进入；首屏有场景或明确降级入口；加载失败可重试 | FR-PUB-001、FR-PUB-004、FR-FALLBACK-001 |
| AC-02 | 三维漫游 | 鼠标和触控可旋转、缩放、平移；相机有边界；长时操作不卡死 | FR-SCENE-004、FR-SCENE-005 |

### 11.2 准确性和安全验收方法

1. 意图测试集不少于 300 条，覆盖四类意图、别名、错别字、近音词、复合意图、CLARIFY 和 UNKNOWN。测试集不得全部来自开发过程中使用的训练示例。
2. RAG 测试集至少包括 60 条可回答问题、30 条无依据问题、10 条过期资料问题和 10 条诱导编造问题。所有学校事实回答要求人工核对来源。
3. 路径测试选取至少 20 组起终点，包括正常路线、不可达终点、起点吸附、跨越障碍和清除路线。检查组件的可通行边和视觉路线是否一致。
4. 语音测试至少覆盖安静室内、普通手机麦克风、正常语速和中等噪声场景。无法达到第三方服务本身能力边界时，必须记录实测条件和降级结果，不能虚报达标。
5. 安全测试包含未登录访问、越权修改、上传危险文件、注入文本、敏感信息泄露、日志脱敏、会话过期和重复提交。
6. 每次第三方模型、提示模板、知识库索引或路径数据变更后，执行意图与拒答回归，防止模型升级造成事实风险回升。

### 11.4 阶段放行标准

只有当以下条件全部满足时，PRD 方可作为下一阶段的设计基线：

1. 项目负责人确认系统范围、优先级和四类核心意图。
2. 校方资料负责人确认可公开的学校事实、名称、坐标来源和占位处理方式。
3. 项目负责人确认性能、并发、准确率和安全指标，或书面调整数值。
4. 明确正式发布、课程答辩或离线演示的使用场景，以及是否需要学校品牌和内容授权。
5. 本文件第 13 节的待确认项有明确责任人、截止时间和处理结论。

### 12.2 外部依赖

1. 校方提供或确认可用于三维建模的校园平面图、建筑名称、道路通行规则、点位坐标和公开宣传素材。
2. 校方审核学校概况、招生、报到、开放时间和路线讲解内容。
3. 至少一个兼容标准接口的大模型、语音识别和语音合成服务，以及相应额度。
4. 可运行 Three.js、Spring Boot 和 MySQL 的开发、测试和部署环境。
5. 正式发布所需域名、HTTPS 证书、备案或学校门户接入安排。
6. 网络环境允许访问第三方 AI 服务；离线演示环境具备预置数据和可选本地模型。

### 12.3 关键约束

1. 前端采用 Vue 3 与 Three.js；后端采用 Spring Boot、MyBatis-Plus 与 MySQL。模型、语音和 AI 服务通过后端适配层接入。
2. 系统不得把未审核内容直接发布给公众，也不得把第三方模型输出当作学校事实来源。
3. 三维场景以轻量单体建模和交互性能优先，不追求照片级还原。
4. 公众端优先免登录使用，后台必须有独立鉴权。
5. 在本科毕业设计周期内，核心功能可演示、关键算法可测试、部署说明可复现的优先级高于增加视觉特效和业务扩展。
